Was ist Agentic Coding?

Agentic Coding ist eine Arbeitsweise, bei der ein KI-System eine Entwicklungsaufgabe über mehrere Schritte selbst bearbeitet. Innerhalb seiner Zugriffsrechte liest es Projektdateien, ändert Code, führt Befehle und Tests aus und wertet das Ergebnis aus. Die Zwischenschritte wählt es selbst und passt sein Vorgehen an, sobald es Neues erfährt. Der Mensch legt fest, welches Problem gelöst werden soll, welche Grenzen gelten und woran eine gute Lösung erkennbar ist.

[hu_abb id="agent-schleife"]

Die Rückkopplung macht den Unterschied

[hu_notiz label="Quelle"]Anthropic, Building effective agents.[/hu_notiz]

„Agentisch“ beschreibt diesen Handlungsspielraum. Der entscheidende Mechanismus ist eine Rückkopplung: Das System handelt, beobachtet das Ergebnis und entscheidet über den nächsten Schritt. Anthropic unterscheidet genau danach. Bei einem Workflow sind die Schritte im Code fest vorgegeben, ein Agent steuert seinen Ablauf und seine Werkzeuge selbst.

Daraus folgt der Unterschied zur Codevervollständigung. Eine Vervollständigung schlägt an einer Stelle Text vor. Ein Coding-Agent arbeitet an einer Aufgabe über mehrere Dateien und Schritte hinweg, bis eine Abbruchbedingung erreicht ist: Die Tests laufen durch, ein Schrittlimit ist erreicht, oder er braucht eine Entscheidung, die ihm nicht zusteht.

Dass sich gerade Programmierung für Agenten eignet, hat einen nüchternen Grund. Code lässt sich ausführen und testen. Der Agent bekommt nach jedem Schritt eine Rückmeldung aus der Umgebung, statt sich auf seine eigene Einschätzung zu verlassen. Eine automatische Prüfung findet allerdings nur, wonach sie fragt. Ob die Lösung zum größeren System passt, beurteilt weiterhin ein Mensch.

Was ist der Unterschied zwischen Agentic Coding und Vibe Coding?

Beim Vibe Coding beschreibt man, was man will, und vertraut dem Ergebnis, ohne den Code genau zu prüfen. Beim Agentic Coding ist die Prüfung fester Bestandteil der Arbeit: Jemand formuliert den Auftrag so, dass er sich abnehmen lässt, und nimmt ihn ab. Die Werkzeuge sind oft dieselben. Der Unterschied liegt darin, wer steuert und wer für das Ergebnis geradesteht.

Den Begriff Vibe Coding hat Andrej Karpathy Anfang 2025 geprägt. Das Verfahren funktioniert, solange ein Fehler nichts kostet. Für die professionelle Variante hat sich zusätzlich der Begriff Agentic Engineering verbreitet. Gemeint ist dasselbe Prinzip mit einem klaren Anspruch: Coding-Agenten verstärken vorhandene Fachkenntnis, sie ersetzen kein Urteilsvermögen.

Je teurer ein Fehler wäre, desto mehr hängt an Auftrag und Abnahme.

Welche Werkzeuge gibt es für Agentic Coding?

Werkzeuge für Agentic Coding gibt es in drei Bauformen: als Agent im Terminal, als Agent in der Entwicklungsumgebung und als Hintergrund-Agent, der in einer Cloud-Umgebung arbeitet und einen Pull Request zurückgibt. Die Produktnamen ändern sich schnell, die Bauformen kaum. Entscheidend ist, wo der Agent arbeitet und wie viel er ohne Rückfrage darf.

Wie funktioniert Agentic Coding an einer Website?

Agentic Coding an einer Website funktioniert wie die Arbeit eines neuen Entwicklers, der Zugang zur Testumgebung hat. Erscheinen auf einer WordPress-Website Formularanfragen gelegentlich nicht im CRM, untersucht der Agent zuerst, wie das Formular aufgebaut ist. Dann verfolgt er die Verarbeitung vom Absenden bis zur Schnittstelle, sucht nach Ursachen und entwickelt eine Änderung. Scheitert eine Prüfung, fließt ihr Ergebnis in den nächsten Versuch ein.

Der Auftrag entscheidet über die Untersuchung

Was bedeutet „gelegentlich“? Betrifft es bestimmte Eingaben? Zeigt das Formular trotzdem eine Erfolgsmeldung? Geht die Anfrage verloren oder kommt sie verspätet an? Welche Daten dürfen zur Fehlersuche protokolliert werden, ohne gegen den Datenschutz zu verstoßen?

Diese Fragen bilden den fachlichen Rahmen. Fehlt er, geht auch eine technisch plausible Änderung am eigentlichen Problem vorbei. So könnte der Auftrag aussehen:

  1. Ziel Jede abgeschickte Anfrage landet im CRM. Schlägt die Übertragung fehl, wird sie gespeichert und erneut versucht.
  2. Ausgangslage Ein Teil der Anfragen fehlt im CRM, das Formular meldet trotzdem Erfolg. Betroffene Fälle mit Zeitstempel liegen bei.
  3. Grenzen Nur in der Testumgebung arbeiten. Keine neuen Plugins. Keine personenbezogenen Daten ins Log, nur Zeitpunkt, Formular und Fehlercode.
  4. Abnahme Eine Testreihe schickt Anfragen in Serie, alle kommen an. Eine simulierte CRM-Störung erzeugt einen sichtbaren Fehlerzustand und einen erneuten Versuch.
  5. Übergabe Die Änderung kommt als Pull Request mit einer kurzen Begründung, welche Ursache gefunden wurde.

Der fünfte Punkt wird oft vergessen. Ohne Begründung lässt sich nicht beurteilen, ob der Agent die Ursache behoben oder nur das Symptom verdeckt hat.

Eine Aufgabe braucht einen überprüfbaren Zielzustand. Wer ihn nicht formulieren kann, sollte noch nicht delegieren, sondern erst klären.

Aus meiner Praxis

Änderungen an dieser Website setze ich mit Coding-Agenten um. Jede Änderung kommt als Pull Request und durchläuft automatische Prüfungen. Bei einem Umbau sollte ein Agent eine Seite nach einer neuen Vorlage gestalten. In der Vorlage war der Anfrage-Button nur ein Platzhalter, und mein Auftrag sagte nicht ausdrücklich, dass das bestehende Formular erhalten bleiben muss. Aus dem Formular wurde ein einfacher E-Mail-Link. Technisch sauber umgesetzt, fachlich falsch. Keine der automatischen Prüfungen hat es bemerkt, weil keine danach gefragt hat.

[hu_pruefliste id="agent-auftrag" titel="Prüfliste: Auftrag an einen Coding-Agenten"]
  1. Das Ziel ist als Zustand beschrieben, nicht als Tätigkeit: „Jede Anfrage kommt an“, nicht „Formular überarbeiten“.
  2. Die Ausgangslage enthält echte Beispiele, nicht nur eine Vermutung.
  3. Die Grenzen stehen fest: welche Umgebung, welche Dateien, keine neuen Abhängigkeiten ohne Rückfrage.
  4. Keine echten Zugangsdaten und keine Kundendaten im Arbeitsbereich des Agenten.
  5. Die Abnahmekriterien sind aufgeschrieben, bevor der Agent startet, und ohne den Code verständlich.
  6. Es ist klar, wie das Ergebnis unter realistischen Bedingungen geprüft wird.
  7. Die Übergabe kommt als Pull Request mit Begründung der gefundenen Ursache.
  8. Eine Person ist benannt, die freigibt und danach für die Lösung zuständig ist.
[/hu_pruefliste]

Warum ist Agentic Coding wichtig?

Agentic Coding ist wichtig, weil sich damit größere Teile der Umsetzung delegieren lassen, nicht nur einzelne Zeilen. Daraus können Veränderungen entstehen, die über eingesparte Arbeitsschritte hinausgehen: Kleine Vorhaben werden wirtschaftlich, Ideen lassen sich früher prüfen, und Fachwissen fließt direkter in Software ein. Wie stark das eintritt, hängt davon ab, wie zuverlässig die Systeme arbeiten und wie gut Unternehmen sie in ihre Abläufe einbinden.

Drei mögliche Folgen

  1. Kleine Vorhaben werden wirtschaftlich Eine interne Auswertung, eine Schnittstellenanpassung, ein kleines Werkzeug für einen wiederkehrenden Prozess: Vieles scheitert heute daran, dass der Aufwand größer wirkt als der Nutzen. Sinkt der Entwicklungsaufwand, rechnet sich mehr davon, vorausgesetzt, Prüfung, Betrieb und Wartung sind mitgedacht.
  2. Ideen werden früher prüfbar Ein funktionsfähiger Prototyp klärt Anforderungen schneller als jedes Konzeptpapier. Nutzer sehen, was gemeint ist, und geben konkrete Rückmeldungen. Der Nutzen entsteht erst, wenn diese Rückmeldungen in die weitere Entwicklung eingehen.
  3. Fachwissen fließt direkter in Software ein Wer einen Geschäftsprozess gut kennt, kann Anforderungen präzise beschreiben und fachliche Fehler erkennen. Coding-Agenten machen die technische Umsetzung zugänglicher. Die Zusammenarbeit zwischen Fachabteilung und Entwicklung bekommt dadurch eine neue Form.

Werden Projekte durch Agentic Coding schneller?

Projekte werden durch Agentic Coding nicht automatisch schneller. Der erste Entwurf entsteht meist zügig, aber zur Projektarbeit gehören auch Auftrag, Rückfragen, Kontrolle, Korrekturen und Integration. Ein schneller Entwurf verkürzt nur einen dieser Schritte. Kontrollierte Studien liefern bisher keine belastbare Zahl für die Zeitersparnis im Projekt.

Wo liegen die Fehlerquellen beim Agentic Coding?

Die größte Fehlerquelle beim Agentic Coding ist eine unvollständige Anforderung, die der Agent sehr konsequent umsetzt. Dazu kommen übersehene Regeln des bestehenden Systems, unnötige neue Abhängigkeiten und Lösungen, die in der Testumgebung funktionieren und unter realen Bedingungen scheitern. Weil der Agent in Schleifen arbeitet, können sich kleine Fehler über mehrere Schritte verstärken.

Drei Ebenen getrennt prüfen

  • Funktion: Erfüllt die Änderung die vereinbarten Anforderungen?
  • Einbindung: Passt sie zum bestehenden System, seinen Schnittstellen und Betriebsabläufen?
  • Wirkung: Hilft sie den Menschen, für die sie entwickelt wurde?

Beim Formularbeispiel kann eine automatische Prüfung bestätigen, dass bestimmte Eingaben verarbeitet werden. Ob die richtige Person im Vertrieb eine brauchbare Anfrage erhält, verlangt eine Prüfung des gesamten Ablaufs.

Eine besonders wichtige Grenze betrifft die Prüfung selbst. Leitet dieselbe KI die Lösung und deren Tests aus einer missverstandenen Anforderung ab, passen beide zusammen und bestätigen trotzdem das falsche Verhalten.

Abnahmekriterien entstehen vor dem Code und unabhängig von ihm.

Zugriffsrechte sind eine Projektentscheidung

[hu_notiz label="Quelle"]Anthropic empfiehlt für Agenten ausgiebige Tests in abgeschotteten Umgebungen, klare Abbruchbedingungen und Schutzmechanismen, Building effective agents.[/hu_notiz]

Ein Agent, der Befehle ausführen darf, braucht dieselbe Sorgfalt wie ein neuer Mitarbeiter mit Serverzugang. Vier Regeln decken die meisten Risiken ab:

  • Getrennte Umgebung. Der Agent arbeitet auf einer Kopie oder in einer Testumgebung, nie direkt auf der Live-Website.
  • Keine echten Zugangsdaten. Passwörter, API-Schlüssel und Kundendaten gehören nicht in seinen Arbeitsbereich.
  • Freigabe durch einen Menschen. Änderungen kommen als Pull Request und gehen erst nach Prüfung live.
  • Fremde Inhalte sind Daten, keine Anweisungen. Ein Agent, der Webseiten, Tickets oder Dokumente liest, kann darin versteckte Anweisungen finden. Je mehr er darf, desto wichtiger ist diese Trennung.

Was verändert Agentic Coding für Entwickler, Agenturen und Auftraggeber?

Agentic Coding verschiebt bei allen drei die Arbeit vom Schreiben zum Beschreiben und Prüfen. Entwickler brauchen weiterhin technisches Verständnis, vermutlich mehr als vorher, weil sie fremden Code in größerer Menge beurteilen. Agenturen müssen Prüfung und Freigabe so ausbauen, dass sie mit der Umsetzung mithalten. Auftraggeber sollten nicht fragen, ob ein Dienstleister mit Agenten arbeitet, sondern wie er die Ergebnisse prüft.

Agenturen: Die Warteschlange wandert

Wenn Änderungen schneller entstehen, müssen Besprechung, Prüfung und Freigabe mithalten. Sonst wächst nur die Warteschlange vor dem nächsten Arbeitsschritt. Wer Prüfung und Freigabe nicht im eigenen Team abbilden kann, holt sie sich als Kapazität dazu, etwa über White-Label-Entwicklung.

Auftraggeber: vier Fragen an jedes Angebot

  • Welches Problem soll die Änderung lösen?
  • Woran wird das Ergebnis abgenommen?
  • Wie wird es unter realistischen Bedingungen geprüft?
  • Wer betreut die Lösung nach der Veröffentlichung?

Dass ein Dienstleister mit Coding-Agenten arbeitet, sagt für sich genommen wenig über die Qualität eines Projekts. Aussagekräftig wird die Arbeitsweise durch nachvollziehbare Entscheidungen und geprüfte Ergebnisse. Eine gute Gegenfrage im Erstgespräch: Woran sehe ich, dass eine Änderung geprüft wurde, bevor sie live ging?

Welche Fähigkeit wird durch Agentic Coding wertvoller?

Am wertvollsten wird die Fähigkeit, eine überzeugend wirkende Lösung von einer tatsächlich geeigneten zu unterscheiden. Dafür braucht es Verständnis für Nutzer, Geschäftsprozesse und technische Zusammenhänge, und die Bereitschaft, Anforderungen zu hinterfragen und eine unnötige Funktion zu verwerfen. Wenn Agenten mehr Umsetzung ermöglichen, wächst die Zahl der Entscheidungen darüber, was gebaut werden sollte.

Auswahl statt Ausstoß

Gute Entwicklung muss diese Auswahl beherrschen. Ihr Wert zeigt sich nicht daran, wie viel Code entsteht, sondern daran, ob aus einer Möglichkeit eine verlässliche, nützliche Lösung wird.

Der Agent baut. Ob es live geht, entscheidet ein Mensch, der weiß, wofür.

Häufige Fragen zu Agentic Coding

Was ist Agentic Engineering?

Agentic Engineering bezeichnet den professionellen Einsatz von Coding-Agenten in Projekten, die andere Menschen betreiben und warten. Die Agenten übernehmen Umsetzung und Tests, Fachleute geben Ziel und Grenzen vor, prüfen das Ergebnis und verantworten, was live geht. Der Begriff grenzt diese Arbeitsweise bewusst vom Vibe Coding ab, bei dem das Ergebnis ohne genaue Prüfung übernommen wird.

Braucht man noch Entwickler, wenn KI-Agenten programmieren?

Ja, man braucht weiterhin Entwickler. Jemand muss Aufgaben abgrenzen, fachliche und technische Fehler erkennen und verantworten, was live geht. Die Arbeit verschiebt sich vom Schreiben jeder Zeile zum Beschreiben, Prüfen und Entscheiden. Wer Code nicht lesen kann, kann auch nicht beurteilen, ob ein Agent die Ursache behoben oder nur das Symptom verdeckt hat.

Ist Agentic Coding mit Kundendaten sicher?

Agentic Coding ist mit Kundendaten nur dann vertretbar, wenn der Agent gar nicht an sie herankommt. Das heißt: Arbeit in einer getrennten Testumgebung mit Beispieldaten, keine echten Zugangsdaten im Arbeitsbereich und Freigabe jeder Änderung durch einen Menschen. Welche Daten ein Werkzeug an seinen Anbieter überträgt, gehört vor dem Einsatz in die Datenschutzprüfung.

Lohnt sich Agentic Coding für eine WordPress-Website?

Für klar abgegrenzte Aufgaben lohnt sich Agentic Coding auch bei einer WordPress-Website: Fehlersuche, Anpassungen am Theme, Schnittstellen zu CRM und Tracking, automatische Tests. Für Entscheidungen über Inhalte, Seitenstruktur und Angebot lohnt es sich nicht. Die bleiben bei dem Menschen, der das Geschäft und seine Kunden kennt.

Wie formuliert man einen guten Auftrag an einen Coding-Agenten?

Ein guter Auftrag an einen Coding-Agenten beschreibt das Ziel als überprüfbaren Zustand, nennt die Ausgangslage mit echten Beispielen, legt Grenzen für Umgebung, Dateien und Abhängigkeiten fest und schreibt die Abnahmekriterien auf, bevor der Agent startet. Dazu gehört, wie das Ergebnis übergeben wird: als Pull Request mit einer Begründung, welche Ursache gefunden wurde.
